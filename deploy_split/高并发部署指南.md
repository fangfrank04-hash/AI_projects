# AI 监考服务 高并发部署指南（同步方案）

> 适用场景：80~120 台电脑每 5~10 秒截图一次，Java **同步调用**（发一张等一张返回），
> 峰值约 **24 张/秒**，每张需几百毫秒内返回。
> 架构已确认为**同步**（组长 2026-07-30 确认："先同步的，应该能满足要求"）。

---

## 一、为什么同步方案能扛住高并发

单张识别耗时约 150ms，属于"快接口"，同步 + 横向扩展即可，无需上消息队列（那是为"慢任务"设计的，这里用反而增加复杂度）。

并发能力靠**两级放大**：
1. **单进程内：模型池**（已做）——预创建 N 个识别器实例，多请求真并行（MediaPipe 推理释放 GIL）
2. **单机内：多进程 workers**——`uvicorn --workers N` 开多个进程吃满多核
3. **多机：负载均衡**——多台服务器，Java/Nginx 轮询分发

### 本机压测实测（趋势参考，真实服务器会更好）

| 配置 | QPS | P95 延迟 |
|---|---|---|
| 改造前（单实例+全局锁） | 4.37 | 9.8 s ❌ |
| 改造后 模型池=2 | 9.60 | 2.8 s |
| 改造后 模型池=4 | 10.36 | 2.5 s |

> 结论：模型池让单进程并发翻倍；单进程有天花板（受核数限制），达到 24 QPS 需靠多进程 + 多机。

## 二、单机怎么配（4核16G 服务器为例）

### 关键参数关系（重要，别配错）

```
单机总并行度 ≈ workers 进程数 × 每进程模型池大小
CPU 核数是硬上限：workers × pool 不要超过核数太多，否则互相抢 CPU 反而变慢
```

**4 核机器推荐**：`workers=2` + `PROCTOR_POOL_SIZE=2`（总并行 4，刚好匹配 4 核），预估单机 ~15 QPS。

### 单机多进程配置（已默认配好）

本目录的 `docker-compose.yml` **已默认配好** `command:`（workers=2）和 `PROCTOR_POOL_SIZE=2`，
起来就是多进程。想改进程数，改 `command` 里的 `--workers` 数字即可：

```yaml
services:
  aiproctor:
    image: aiproctor-base:1.1.0
    ports:
      - "8000:8000"
    environment:
      - PROCTOR_POOL_SIZE=2      # 每进程模型池
    command: ["/app/.venv/bin/python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "2"]
    restart: unless-stopped
```

> 注意：`workers` 每个进程都会各自加载 `PROCTOR_POOL_SIZE` 个模型，内存占用 = workers × pool × 约400MB。
> 4核16G 跑 workers=2 × pool=2 = 4 个实例 ≈ 1.6GB，很宽裕。

## 三、多机部署（扛住 24 QPS 峰值的关键）

### 架构图

```
                  ┌─────────────────┐
   Java 监控端 ──▶│ 负载均衡         │──▶ 服务器A: aiproctor (workers=2)
   (80~120台)     │ (Nginx 或        │──▶ 服务器B: aiproctor (workers=2)
                  │  Java 端轮询)    │
                  └─────────────────┘
   2 台 4核机 ≈ 30 QPS，稳扛 24 峰值，且挂一台另一台顶（容错）
```

### 两种负载均衡方式（选一）

**方式一：Java 端直接轮询（最简单，无需额外组件）**
Java 侧配置多个服务地址，用 Ribbon/LoadBalancer 或自己轮询：
```
http://服务器A_IP:8000/upload_face
http://服务器B_IP:8000/upload_face
```
每次请求轮流发给 A、B。

**方式二：Nginx 反向代理（统一入口）**
内网起一个 Nginx，Java 只调 Nginx 一个地址：
```nginx
upstream aiproctor {
    server 服务器A_IP:8000;
    server 服务器B_IP:8000;
}
server {
    listen 80;
    location / {
        proxy_pass http://aiproctor;
        proxy_read_timeout 30s;
    }
}
```
Java 调 `http://Nginx_IP/upload_face` 即可，Nginx 自动分发。

## 四、上线前建议做的容量测试

用项目自带压测脚本，在**真实内网服务器**上测出单机真实 QPS，再决定起几台：

```bash
# 在能访问服务的机器上跑（scripts/load_test.py 在代码仓库里）
python scripts/load_test.py --url http://服务器IP:8000 --concurrency 24 --total 240
```
看输出的"吞吐 QPS"和"P95 延迟"：
- 单机 QPS × 台数 ≥ 24，且 P95 < 你能接受的延迟 → 达标
- 不够就加 workers 或加机器

## 五、给 Java 同事的对接要点（同步）

- 调用：`POST http://<服务/负载均衡地址>/upload_face`，multipart 表单，必传 `user_id` 和图片字段 `file`
- **同步等待**：请求会阻塞到识别完成才返回（正常几百毫秒），建议客户端超时设 **10~30 秒**（防止极端排队）
- 可选参数：`max_left_angle` 等 4 个面部角度阈值（不传用默认，见同目录《内网部署步骤_分离模式.md》）
- 黑屏响应使用 `exception_code=1001`；同一进程内连续黑屏由 `notify` 去重。由于不使用 Redis，负载均衡到不同进程/服务器时不能保证全局只提示一次
- **动作类型归并**（原 8 种细类 → 6 大类；黑屏走异常码）：
  | 大类 | action_type |
  |---|---|
  | 视线偏移 | `gaze_away` + `turn_head` |
  | 离开座位 | `leave_seat` + `turn_body` |
  | 其余 | `normal` / `multi_person` / `phone_call` / `stretch_arm` 一对一 |

## 六、调优速查

| 想解决 | 怎么调 |
|---|---|
| 单机吞吐不够 | 加 `--workers`（不超过核数）、加 `PROCTOR_POOL_SIZE` |
| 内存不够/OOM | 减小 workers 或 pool |
| 峰值扛不住 | 加机器（最有效），Java/Nginx 加进负载均衡池 |
| 偶发排队超时 | 加机器分摊；把 Java 客户端超时调大 |
