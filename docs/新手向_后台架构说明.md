> 这份文档是写给「不懂规范后台开发」的你的。不讲大道理，只回答你关心的四个问题：
> 1. 每个文件夹是干嘛的、为什么要这么分？
> 2. 我原来写在 `main.py` 里的接口，现在跑哪去了？
> 3. 一个请求进来，代码是怎么一步步跑的？

## 一、先用一个「饭店」的比喻理解分层

你原来的写法，相当于**一个人（main.py）从点菜、炒菜、洗碗、收钱全包**。代码能跑，但一旦出问题，你不知道是哪一步坏了，改一个地方容易牵连一片。

规范后台的做法，是**把一个饭店拆成不同岗位**，各管一段：

| 饭店岗位 | 项目里的层 | 文件夹 | 职责（只干这一件事） |
|---------|-----------|--------|--------------------|
| 前台服务员 | 路由层 API | `app/api/` | 收客人的请求、把菜端出去。**不炒菜** |
| 后厨主厨 | 业务层 Service | `app/services/` | 真正干活：洗菜、协调、处理各种意外 |
| 专业厨师 | 模型层 ML | `app/ml/` | 只负责最核心的手艺（AI 图像识别） |
| 菜单/餐具规格 | 数据模型 Schemas | `app/schemas/` | 规定「菜品长什么样」——请求和返回的格式 |
| 饭店的水电/规章 | 基础设施 Core | `app/core/` | 配置、日志、异常处理这些全店通用的东西 |

**为什么要拆？** 一句话：**让每个文件只有一个「改动理由」**。
- 想换接口地址 → 只动 `api/`
- 想改识别逻辑 → 只动 `ml/`
- 想改返回格式 → 只动 `schemas/`

出了 bug，你能一眼定位到是哪一层的问题，而不是在一个几百行的大文件里大海捞针。这就是「规范」带来的最直接好处。

│   └── v1/

│   ├── image_proctor.py    #   核心检测逻辑（570 行，你项目最值钱的部分）
│   ├── front_camera.py     #   前置摄像头相关（历史代码）
│   └── Toolkit.py          #   工具函数
│
├── schemas/                # 【数据模型层】规定请求/返回长什么样
│   └── proctor.py          #   统一响应体 {code, message, data} + 各种枚举
│
└── core/                   # 【基础设施层】全店通用的东西

## 三、你最关心的：原来 main.py 里的接口去哪了？

**答案：接口本身没变，还是那三个地址，只是把「定义」和「干活」拆开了。**

### 重构前（你原来的写法，示意）
```python
# main.py —— 一个文件全包
@app.get("/test")
def test():
    # 读图片
    # 转格式
    # 调 AI 模型
    # 拼装返回...
    # 全写在这里，几十行
    return 一堆文字
```

### 重构后（现在的写法）——拆成了 3 段，各司其职

**第 1 段：接口定义**，在 `app/api/v1/proctor.py`：
```python
@router.get("/test", response_model=ApiResponse)
def test():
    """测试人脸识别（使用内置测试图片）"""
    return proctor_service.analyze_test_image()   # ← 自己不干活，交给 service
```
👉 前台只喊一嗓子「有人点了 test 这道菜」，然后把活扔给后厨。

**第 2 段：真正干活**，在 `app/services/proctor_service.py`：
```python
def analyze_test_image() -> ApiResponse:
    # 1. 检查测试图片在不在
    # 2. 打开图片、转成 RGB
    # 3. 调用 AI 模型 ImageProctor().analyze()
    # 4. 把结果包装成统一格式返回
    return ApiResponse.success(data=..., message="识别成功")
```
👉 后厨做了所有脏活累活，包括处理「图片不存在」「图片打不开」这些意外。

**第 3 段：AI 识别**，在 `app/ml/image_proctor.py`：
```python
def analyze(self, pil_img) -> ProctorResult:
    # MediaPipe 检测人脸角度、姿态、多人...
    # 返回结构化结果
```
👉 专业厨师只管手艺，不关心图片是谁传来的、结果给谁看。

**三个接口的对照表**（地址完全没变，你的前端/测试脚本不用改）：

| 接口地址 | 定义在哪（api层） | 干活在哪（service层） |
|---------|-----------------|---------------------|
| `GET /test` | proctor.py 的 `test()` | `analyze_test_image()` |
| `GET /ping` | proctor.py 的 `ping()` | 太简单，直接返回，没进 service |
| `POST /upload_face` | proctor.py 的 `upload_face()` | `analyze_uploaded_face()` |

## 三点五、面部角度阈值：可传参数覆盖（2026-07-20 新增）

判断「视线偏移 / 转头方向」靠的是头部的左右角(yaw)和上下角(pitch)，超过阈值就判为看向某个方向。
这 4 个阈值现在**可由调用方（如 Java）通过接口参数覆盖**：

- **不传任何参数** → 用代码里的默认值，行为和改造前**完全一样**。
- **传了参数** → 只对这一次请求生效（不会污染其他请求），每个参数都能单独传或省略。

| 参数名 | 默认值 | 含义 |
|--------|-------:|------|
| `max_left_angle` | 6 | 左右角 > 该值 → 向左看 |
| `max_right_angle` | -6 | 左右角 < 该值 → 向右看 |
| `max_up_angle` | 6 | 上下角 > 该值 → 向上看 |
| `max_down_angle` | -1 | 上下角 < 该值 → 向下看 |

**两个接口的传参方式不同**（因为 HTTP 方法不同）：

- `GET /test`：参数放在 **URL query** 里，例如 `GET /test?max_left_angle=10&max_right_angle=-10`
- `POST /upload_face`：参数作为 **multipart 表单字段**，跟图片一起传（字段名同上）

默认值写在 `app/ml/image_proctor.py` 顶部的 `DEFAULT_MAX_*_ANGLE` 常量里，想改默认值只改这一处。
阈值的实际生效逻辑：service 层用 `_build_face_angles()` 把参数组装成 `FaceAngleThresholds`，
传给 `ImageProctor.analyze()`，在锁内临时套用、用完自动回默认。

## 四、一个请求进来，代码怎么一步步跑？（全链路追踪）

以「用户上传一张图片」`POST /upload_face` 为例，跟着箭头走一遍：

```
用户上传图片
    │
    ▼
① app/api/v1/proctor.py  →  upload_face(file)
    │  「前台收到图片，转手交给后厨」
    ▼
② app/services/proctor_service.py  →  analyze_uploaded_face(file)
    │  a. 校验：是图片吗？（不是 → 返回错误码 400）
    │  b. 校验：太大了吗？（>10MB → 返回错误码 413）
    │  c. 打开图片（打不开 → 返回错误码 400）
    ▼
③ app/ml/image_proctor.py  →  analyze(image)
    │  「AI 真正识别：视线、动作、人数」
    │  返回 ProctorResult（结构化结果）
    ▼
④ app/services/proctor_service.py
    │  把 ProctorResult 翻译成 DetectionData
    │  用 ApiResponse.success() 包装
    ▼
⑤ app/schemas/proctor.py 定义的格式，最终返回给用户：
    {
      "code": 200,
      "message": "识别成功",
      "data": {
        "warning": true,
        "action_type": "phone_call",
        "action_label": "警告，考生疑似打电话",
        "warning_count": 1,
        "person_count": 1
      }
    }
```

**对比你原来的返回**（`m_listText`，长这样）：
```
[("警告，考生疑似打电话", (255,0,0)), ("1", ...)]
```
👉 原来返回的是「UI 文字 + 颜色」混在一起的元组，前端得自己猜怎么解析。
👉 现在返回的是**机器可读的结构化数据**：`action_type: "phone_call"` 前端一看就懂，颜色这种「怎么显示」的事交给前端自己决定。这就是「大厂后台规范」的核心思想——**后台给数据，前端管显示，两边不打架**。

## 五、关键概念速查（看代码时遇到别慌）

### 1. `{code, message, data}` 是什么？
定义在 `app/schemas/proctor.py` 的 `ApiResponse`：
- `code`：**业务**状态码，复用 HTTP 状态码语义。`200` = 成功，非 200 = 各种错误。
- `message`：给人看的提示文字。
- `data`：真正的数据。

**为什么用 HTTP 风格的码（200/400/404/500）？** 这样前端一看 `code` 就能用熟悉的 HTTP 语义判断结果，不用额外背一套业务码表。我们遵循你们内网项目的约定。

### 2. 错误码表（在 `StatusCode` 枚举里）
| 码 | 含义 |
|----|------|
| `200` | 成功 |
| `400` | 请求有误（文件类型不对 / 为空 / 图片无法解析） |
| `404` | 资源不存在（如测试图片缺失） |
| `413` | 上传图片过大 |
| `500` | 服务内部错误 |

规律：`4xx` 是「你（客户端）传的东西有问题」，`5xx` 是「我（服务器）自己出问题了」——和 HTTP 状态码的含义一致。

### 3. 枚举（Enum）为什么好？
`action_type` 用的是 `ActionType` 枚举，取值只能是 `normal / gaze_away / phone_call ...` 这几个固定值。好处：**打错字编译器/编辑器会提醒你**，不会出现有的地方写 `"phone_call"`、有的地方写 `"phonecall"` 这种前后不一致的 bug。

### 4. 全局异常处理（`app/core/exceptions.py`）
万一代码某处崩了（比如 AI 模型抛异常），不会把一大堆吓人的报错堆栈直接甩给用户，而是统一包装成 `{"code": 500, "message": "服务内部错误"}`。同时后台日志里会记录真实错误，方便你排查。这是「生产级」后台的基本要求。

### 5. 日志替代 print（`app/core/logging.py`）
你原来可能用 `print` 打印调试信息。规范做法是用 `logging`：可以分级别（DEBUG/INFO/WARNING/ERROR）、可以统一开关、带时间戳。生产环境靠日志排查问题，而不是满屏 print。

## 六、【重点】你怎么自己动手验收？

不用懂代码细节，跟着做下面 4 步，就能判断「写得对不对、能不能跑」。

### 验收第 1 步：跑自动化测试（最重要）
在项目根目录执行：
```bash
uv run pytest -v
```
**看什么**：最后一行如果是 `19 passed`（全绿、passed），说明所有功能都正常。这些测试会自动模拟「上传正常图片」「上传非图片」「上传坏图片」等场景，帮你验证接口行为对不对。**这是最省事的验收方式——机器帮你验，比你手点靠谱。**

### 验收第 2 步：跑代码规范检查
```bash
uv run ruff check app tests
```
**看什么**：出现 `All checks passed!` 就说明代码符合 Python 规范（命名、import 顺序、无多余代码等）。

### 验收第 3 步：启动服务，用网页点接口
```bash
uv run python -m app.main
```
然后浏览器打开 **http://localhost:8000/docs**
**看什么**：这是自动生成的接口调试页面。你能看到 `/test`、`/ping`、`/upload_face` 三个接口，点开任意一个，点「Try it out」→「Execute」，就能真实调用并看到返回的 `{code, message, data}`。**能在这里点出结果，说明接口是通的。**

### 验收第 4 步：核对返回格式
调 `/test` 或上传图片后，确认返回的 JSON 长这样（有 code/message/data 三个字段，data 里有 action_type 等）：
```json
{ "code": 200, "message": "识别成功", "data": { "action_type": "normal", ... } }
```
👉 只要不再是原来那种 `[("文字",(255,0,0))]` 的元组，就说明接口标准化改造成功了。
